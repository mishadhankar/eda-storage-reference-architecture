# Contributing

Contributions and technical review are welcome.

The goal of this project is to develop a vendor-neutral and evidence-based methodology for evaluating storage and data infrastructure for semiconductor Electronic Design Automation (EDA) environments.

## Useful Contributions

Contributions may include:

- corrections or clarifications to technical documentation;
- additional public technical references;
- suggestions for workload-characterization criteria;
- vendor-neutral architecture patterns;
- improvements to evaluation methodology;
- example non-confidential workload profiles;
- recovery and resilience patterns;
- technical-economic evaluation approaches; and
- documentation improvements.

## Vendor Neutrality

Contributions should focus on technical principles rather than product promotion.

Commercial products may be discussed when necessary to illustrate an architecture, benchmark, implementation, or publicly documented technical capability. Product-specific claims should be clearly attributed to their source.

## Evidence and Citations

Technical claims should preferably be supported by publicly accessible sources such as:

- industry standards;
- benchmark specifications;
- peer-reviewed research;
- government publications;
- vendor technical documentation;
- conference materials; or
- established technical publications.

Sources should distinguish measured results from projections, opinions, or marketing claims.

## Confidentiality

Do not contribute:

- confidential employer information;
- customer-identifiable data;
- internal performance results;
- internal pricing or financial information;
- non-public roadmaps;
- proprietary documents; or
- information obtained under a confidentiality obligation.

If you are unsure whether information can be shared publicly, do not submit it.

## Technical Discussion

Where reasonable, discussions should distinguish among:

1. observed workload behavior;
2. architectural assumptions;
3. measured evidence;
4. analytical conclusions; and
5. proposed or experimental ideas.

This helps maintain the technical credibility of the project.

## Pull Requests

When proposing a change:

1. describe the technical problem or improvement;
2. explain the reasoning behind the change;
3. provide supporting sources where applicable; and
4. identify assumptions or limitations.

Substantial architecture changes should preferably be discussed through a GitHub Issue before a pull request is submitted.
